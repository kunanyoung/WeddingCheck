## 2. 한 장 요약

**무엇** — 예식일만 입력하면 32개 업무의 기한이 자동으로 깔리고, 체크만 하면 진행률이
집계되는 개인용 체크리스트. 로그인·서버 없음.

**누구** — 웨딩홀 예약실 직원(주), 웨딩플래너, 예식 담당자.

**왜** — 예약실 업무는 예식 1건당 30개 이상의 확인 사항이 6개월에 걸쳐 흩어집니다.
종이 양식은 진행률이 안 보이고, 회사 CRM은 **이직하면 그대로 잃습니다.**

**어떻게 다른가** — 고객 개인정보를 저장하지 않습니다. 이름·연락처 필드가 애초에 없고,
예식은 `5/16(토) 13:00 그랜드홀` 처럼 날짜·시간·홀로 구분합니다.

## 3. 이 프로젝트의 핵심 설계 결정 5가지

### ① 개인정보는 "안 쓰기"가 아니라 "쓸 수 없게" 만든다

3단 방어로 구조화했습니다. (상세: `01-service-plan.md` §5)

| 단계 | 방법 |
| --- | --- |
| 1차 | 저장 스키마에 이름·전화·주소·이메일·주민번호·금액 **필드가 존재하지 않음** |
| 2차 | 앱이 먼저 별칭을 만들어 줌 (`W-260516-1300` / `5/16(토) 13:00 그랜드홀`) |
| 3차 | 모든 자유 입력에 Zod PII 검사 — 연락처·주민번호·이메일·카드는 **저장 차단**, 금액·주소는 경고 |

이름은 기계적으로 판별할 수 없으므로 차단하지 않고, 입력창 상시 안내 + 온보딩으로 유도합니다.
잔금은 **금액이 아니라 "확인 여부"만** 체크합니다.

### ② 입력이 아니라 체크가 중심

예식 등록의 필수 입력은 **예식일 1개**. 시간·홀은 최근 사용 이력 칩으로 1클릭, 별칭은 선택.
목표는 **20초 이내 등록 · 클릭 2회**.

### ③ 오늘 화면에서 바로 체크된다

예식 상세로 들어가지 않아도 홈에서 체크박스를 누를 수 있습니다. 하루 수십 번 반복되는
동작이라 여기서 클릭 수가 결정됩니다. 앱을 열면 **0클릭**으로 오늘 할 일이 보입니다.

### ④ 템플릿은 예식에 "복사"된다

예식 생성 시 템플릿 항목을 스냅샷으로 복사합니다. 이후 템플릿을 고쳐도 진행 중인 예식은
변하지 않습니다. 웨딩홀을 옮겨도(A홀 → B홀) 템플릿만 추가하면 되고 과거 기록은 그대로입니다.

### ⑤ 파일은 LocalStorage에 넣지 않는다

LocalStorage는 5MB 한계라 식순 PDF 하나로 앱이 죽습니다.
**첨부 Blob은 IndexedDB**, LocalStorage에는 메타데이터만 둡니다.

## 8. 기존 프로토타입(WeddingCheck)과의 관계

이 저장소에는 예약실 **CRM 방향**의 초기 프로토타입이 있습니다(`index.html` · `app.js` ·
`data.js` · `styles.css`). 고객 이름·연락처·계약 정보·공유 링크를 다루는 구조라,
"개인정보를 저장하지 않는 개인 생산성 앱"과는 방향이 반대입니다.

**따라서 부분 수정이 아니라 도메인 지식만 승계하고 데이터 모델·스택을 새로 세웁니다.**

| 프로토타입 | 판정 |
| --- | --- |
| 체크리스트 업무 순서, D-Day·진행률 계산, 접근성·반응형 처리, 토큰 구조 | **승계** |
| 고객 목록·부재중 메모·시식 예약·제휴업체·실적 대시보드·로그인·공유 링크 | **폐기** (개인정보 / 회사 시스템 영역) |
| Vanilla JS 전역 state → Next.js + TypeScript + Zustand | **교체** |
| Rose `#a9455a` + Gowun Batang → Gold `#C8A36B` + Pretendard 단일 | **교체** |

기존 코드는 `legacy/` 로 옮겨 참조용으로 보관합니다. 이관 명령과 승계 대상 코드는
`07-roadmap.md` §6 에 정리했습니다.
