# 07. 개발 우선순위 · MVP 범위 · 확장 계획 · 개발 로드맵

## 1. MVP 범위 (v1.0)

지정된 MVP 8개 기능을 기준으로, 각 기능이 "완성"으로 인정되는 조건을 명시합니다.

| # | 기능 | 포함 | 제외 (v1.1 이후) |
| --- | --- | --- | --- |
| 1 | 체크리스트 | 12카테고리 32항목, 1클릭 체크, 완료시각, 카테고리 접기, 항목 메모, 기한 표시·수정 | 조건부 항목 자동 비활성, 카테고리 일괄 체크 |
| 2 | 진행률 | 원형 + 바, 정수 %, 카테고리별 개수, 100% 피드백 | 카테고리 스택 바 |
| 3 | D-Day | `D-95` / `D-DAY` / `D+3`, 자정 갱신 | — |
| 4 | 일정 자동 생성 | 예식일 → 13마일스톤, 요약 8단계 뷰, 기한 개별 수정, 일정 화면(주간) | 월간 그리드, 마일스톤 일괄 이동 |
| 5 | 메모 | 자유 메모, 예식 연결, 오늘 메모, PII 차단/경고, 수정·삭제 | 태그, 상단 고정 |
| 6 | 템플릿 저장 | 기본 템플릿, 복제, 항목/카테고리 추가·삭제·순서변경, 예식별 스냅샷 | 템플릿 내보내기/공유 |
| 7 | LocalStorage | persist, 마이그레이션 기반, 용량 초과 처리, 전체 삭제 | JSON 백업/복원 |
| 8 | PWA 설치 | manifest, SW, 오프라인 완전 동작, 설치 안내 | 앱 배지, periodicSync |
| + | 검색 | 통합 검색(예식·항목·메모·일정), 결과 이동+하이라이트 | 최근 검색어, 초성 검색 |
| + | 알림 | 인앱 배지 | 브라우저 알림 |
| + | 온보딩 | 3단계 (앱 소개 / 개인정보 원칙 / 로컬 저장 안내) | — |

**MVP에서 의도적으로 빼는 것**: 첨부파일, 브라우저 알림, JSON 백업, 다크모드.
셋 다 중요하지만 "업무를 놓치지 않는다"는 핵심 가치에 직접 기여하지 않거나
(첨부·다크모드) 기술 제약 설명이 더 필요합니다(알림). 단 **JSON 백업은 v1.1 최우선**입니다 —
데이터 유실 리스크가 가장 크기 때문입니다.

## 2. 개발 우선순위

### P0 — 이것 없으면 앱이 아님

| 순서 | 작업 | 이유 |
| --- | --- | --- |
| 1 | 타입 + Zod 스키마 + 기본 템플릿 시드 | 이후 모든 코드의 기반. 여기서 틀리면 전부 고쳐야 함 |
| 2 | Zustand store + persist + 하이드레이션 처리 | Next.js + LocalStorage의 최대 함정 |
| 3 | 날짜 유틸 (D-Day, dueOffset↔dueDate) + 단위 테스트 | 계산 오류는 신뢰를 즉시 잃음 |
| 4 | PII 가드 + 단위 테스트 | 핵심 원칙. 나중에 붙이면 폼을 다시 씀 |
| 5 | 디자인 토큰 + AppShell + 반응형 네비 | 화면 작업의 전제 |
| 6 | 체크리스트 뷰 + 체크 토글 + 진행률 | 앱의 심장 |
| 7 | 예식 등록 폼 + 목록 | 데이터 진입점 |
| 8 | 오늘 화면 | 첫 진입 화면이자 핵심 가치 |

### P1 — 있어야 실무에 쓸 수 있음
템플릿 편집, 메모, 검색, 일정 화면, 온보딩, PWA, 용량 처리

### P2 — v1.1+
JSON 백업 → 첨부 → 브라우저 알림 → 태그/고정 → 보관함 → 다크모드

### 우선순위 판단 기준
`(핵심 가치 기여도 × 사용 빈도) ÷ 구현 비용` 순.
"오늘 화면에서 바로 체크"는 하루 수십 번 쓰이므로 최상위, 첨부는 주 1~2회라 후순위입니다.

## 4. 향후 확장 계획 (v2.0+)

| 기능 | 접근 방식 | 개인정보 원칙과의 관계 | 난이도 |
| --- | --- | --- | --- |
| **Google Calendar 연동** | OAuth는 서버가 필요 → 대안: `.ics` 파일 내보내기(서버 불필요)를 먼저 제공. 양방향 동기화는 서버 도입 결정 후 | 일정 제목에 라벨(`5/16 그랜드홀 · 식권 전달`)만 — 이름 없음 | 중 (ics) / 높음 (OAuth) |
| **iCloud Calendar 연동** | 공식 API 없음 → `.ics` 구독 URL 방식만 현실적. 서버 필요 | 동일 | 높음 |
| **반복 일정** | 매주 토요일 예식처럼 반복 등록 → 예식 카드 일괄 생성 기능으로 구현 | 영향 없음 | 낮음 |
| **백업·복원 (JSON)** | v1.1로 앞당김 | 백업 파일에도 PII 없음 | 낮음 |
| **다크모드** | 토큰에 dark 값 이미 정의됨 | 영향 없음 | 낮음 |
| **엑셀 내보내기** | `xlsx` 라이브러리로 클라이언트 생성. 예식별 체크리스트 시트 | 내보낸 파일에 PII 없음 명시 | 낮음 |
| **PDF 출력** | 인쇄용 CSS(`@media print`)를 먼저 제공 → 브라우저 인쇄로 대체 가능. 필요 시 `pdf-lib` | 동일 | 중 |
| 기기 간 동기화 | 서버 없이는 불가. E2E 암호화된 사용자 소유 저장소(Dropbox/Drive 파일) 방식 검토 | 암호화 전제 필수 | 높음 |
| 다국어 | `messages/ko.ts` 구조 이미 준비 | 영향 없음 | 낮음 |

> **서버 도입 판단 기준** — 다음 중 2개 이상이 요구되면 서버를 검토합니다:
> (a) 기기 간 동기화, (b) 브라우저 종료 중 푸시 알림, (c) 캘린더 양방향 동기화.
> 서버를 도입하는 순간 "개인정보 비저장" 보장이 약해지므로, 도입 시에도
> **체크 상태·기한만 동기화하고 자유 텍스트는 클라이언트 암호화** 원칙을 세웁니다.

## 6. 기존 프로토타입 이관 절차

```bash
# 1) 기존 결과물 보관 (히스토리 유지)
git checkout -b feat/wedding-desk-checklist
mkdir legacy
git mv index.html app.js data.js styles.css assets design README.md legacy/

# 2) 새 앱 생성 (루트)
npx create-next-app@latest . --typescript --tailwind --app --eslint --use-pnpm
pnpm dlx shadcn@latest init

# 3) 문서는 그대로 (docs/ 유지)
# 4) legacy/README.md 상단에 안내 추가:
#    "이 폴더는 예약실 CRM 방향의 초기 프로토타입입니다.
#     현재 제품 방향은 docs/01-service-plan.md §9 를 참고하세요."
```

승계할 코드 자산 (참조용으로 `legacy/` 에서 꺼내 씀):

| 대상 | 위치 | 활용 |
| --- | --- | --- |
| D-Day 계산 | `legacy/app.js` | `lib/date/dday.ts` 로 이식 (기준일 고정값 제거) |
| 진행률 계산 | `legacy/app.js` | `selectors/progress.ts` 로 이식 |
| 반응형 브레이크포인트 | `legacy/styles.css` | 640/768/1024/1280으로 재정렬 |
| 접근성 처리 (`aria-*`, 포커스링, 모션 축소) | `legacy/styles.css`, `app.js` | 그대로 승계 |
| 체크리스트 업무 지식 | `legacy/data.js` `CHECKLIST` | `08-checklist-template.md` 로 재구성 완료 |

**이관하지 않는 것**: `CUSTOMERS`, `MEMOS`(고객명·연락처 포함), `TASTINGS`, `VENDORS`,
`STAFF`, `SHARE_LINK`, 로그인 화면, 히어로 이미지(`assets/hero-photo.webp` — 신규 앱은
사진 없이 토큰 기반 UI).
