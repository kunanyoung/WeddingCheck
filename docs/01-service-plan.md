# 01. 서비스 기획서

## 1. 한 줄 정의

**Wedding Desk Checklist** 는 웨딩홀 예약실 직원이 자기 담당 예식의 준비 업무를
빠뜨리지 않도록 돕는, 로그인 없는 **개인 업무용 체크리스트 웹앱**입니다.

## 2. 왜 만드는가 — 문제 정의

예약실 업무는 예식 1건당 30개가 넘는 확인 사항이 6개월에 걸쳐 흩어져 발생합니다.
현장에서 실제로 쓰이는 도구는 종이 양식, 개인 수첩, 회사 CRM 세 가지인데 각각 문제가 있습니다.

| 도구 | 문제 |
| --- | --- |
| 종이 체크리스트 | 진행률을 한눈에 못 봄, 분실, 여러 건 동시 관리 불가, 퇴근 후 확인 불가 |
| 개인 수첩 · 메모앱 | 예식일 기준 기한 개념이 없어 "언제까지"가 빠짐 |
| 회사 CRM | 개인 업무 단위가 아님, 권한·속도 문제, **이직하면 그대로 잃음** |

세 번째가 핵심입니다. 예약실은 이동이 잦은 직군인데, 업무 노하우가 회사 시스템에 갇혀 있어
이직할 때마다 개인의 업무 체계를 처음부터 다시 만듭니다.

## 3. 해결 방식

1. **예식일만 입력하면 32개 업무의 기한이 자동으로 깔린다** — 입력이 아니라 체크가 중심.
2. **데이터는 내 브라우저에만 있다** — 로그인·서버·계정 없음. 회사가 바뀌어도 앱은 그대로.
3. **개인정보를 구조적으로 저장할 수 없게 만든다** — 이름·연락처 필드가 애초에 없음.
4. **템플릿으로 웨딩홀별 업무 방식을 담는다** — A홀 → B홀 이직 시 템플릿만 추가.

## 4. 무엇이 아닌가 (Non-goals)

| 하지 않는 것 | 이유 |
| --- | --- |
| 고객관리(CRM) | 회사 시스템의 역할. 개인정보를 다루게 됨 |
| 고객 이름·연락처 저장 | 핵심 원칙 위반 |
| 계약금액·정산액 기록 | 개인정보 및 영업기밀. 여부(`잔금 확인`)만 체크 |
| 신랑신부와의 공유 | 공유하는 순간 고객 데이터가 됨 → 프로토타입의 공유 링크 기능 폐기 |
| 팀 협업 · 담당자 배정 | 개인 생산성 도구 범위를 벗어남 |
| 로그인 · 서버 DB | 서버가 없으면 유출 사고도 없음 |
| 사내 게시판 · 제휴업체 DB · 실적 대시보드 | 회사 자산. 프로토타입에서 폐기 |

## 5. 개인정보 비저장 원칙 — 설계로 강제하기

원칙을 문구로만 두면 지켜지지 않습니다. 다음 3단으로 구조화합니다.

### 5-1. 필드 자체를 없앤다 (1차 방어)

저장 스키마에 이름·전화·주소·이메일·주민번호·금액 필드가 **존재하지 않습니다.**
예식을 구분하는 값은 다음 세 가지뿐입니다.

| 필드 | 예시 | 개인정보 여부 |
| --- | --- | --- |
| `date` 예식일 | `2026-05-16` | 아님 (일정 정보) |
| `time` 예식시간 | `13:00` | 아님 |
| `hall` 홀 이름 | `그랜드홀` | 아님 (자사 시설명) |

### 5-2. 자동 식별자로 부른다 (2차 방어)

이름을 쓰고 싶은 욕구를 없애기 위해 앱이 먼저 별칭을 만들어 줍니다.

```
코드:  W-260516-1300        (예식일 + 시간, 자동 생성 · 수정 불가)
표시:  5/16(토) 13:00 그랜드홀   (자동 생성 라벨)
별칭:  (선택) "5월 셋째 주 1부"   ← 사용자 입력, 개인정보 차단 검사 통과 필요
```

별칭 입력란의 placeholder는 `예: 5월 셋째 주 1부 / 가든홀 오후` 이며,
"고객 이름을 적지 않아도 예식일·시간·홀로 충분히 구분됩니다"를 helper text로 항상 노출합니다.

### 5-3. 입력 시점에 차단·경고한다 (3차 방어)

별칭·메모·태그 등 모든 자유 입력에 Zod 스키마 검사를 붙입니다.

| 패턴 | 판정 | 사용자에게 보이는 메시지 |
| --- | --- | --- |
| 휴대폰 번호 `010-1234-5678` | **차단** (저장 불가) | "연락처는 저장할 수 없습니다. 이 앱은 개인정보를 보관하지 않습니다." |
| 주민등록번호 형식 | **차단** | 동일 |
| 이메일 주소 | **차단** | 동일 |
| 카드번호 16자리 | **차단** | 동일 |
| 금액 `1,200,000원` | **경고** (저장은 가능) | "금액은 기록하지 않는 것을 권장합니다." |
| 도로명 주소 형식 | **경고** | "주소로 보이는 내용이 있습니다." |
| 사람 이름 | 검사 불가 → **상시 안내** | 입력창 하단 고정 문구 |

이름은 기계적으로 판별할 수 없으므로 차단하지 않고, 입력창에 상시 안내 문구를 두어
행동을 유도합니다. 첫 실행 온보딩에서도 이 원칙을 한 화면으로 설명합니다.

### 5-4. 첨부파일 정책

식순 PDF·영상 링크·참고 이미지는 업무상 필요하므로 지원하되:

- 파일은 브라우저 IndexedDB에만 저장되고 외부로 전송되지 않음을 명시합니다.
- 첨부 시 1회성 확인 문구: **"개인정보가 포함된 파일은 첨부하지 않는 것을 권장합니다."**
- 파일명은 자동으로 원본 유지하되, 사용자가 바꿀 수 있게 합니다.
- 설정에 "첨부 전체 삭제" 버튼을 둡니다.

## 6. 타깃 사용자

| 페르소나 | 상황 | 핵심 니즈 |
| --- | --- | --- |
| **예약실 담당 3년차** (주 사용자) | 동시 진행 예식 8~15건, 하루 상담 3~4건 | 오늘 뭘 놓쳤는지 30초 안에 확인 |
| **예약실 신입 6개월** | 업무 순서를 아직 못 외움 | 기본 템플릿이 곧 업무 매뉴얼 |
| **웨딩플래너 (프리랜서)** | 여러 홀을 오가며 진행 | 홀별 템플릿 분리 |
| **예식 담당자 (당일 진행)** | 당일 현장, 모바일만 | 당일 카테고리 5항목 원터치 |

## 7. 사용 맥락 — 3가지 시나리오

**아침 출근 직후 (PC, 2분)**
`오늘` 화면 → 지연 항목 확인 → 오늘 기한 항목 체크 → 오늘 메모 1줄.

**상담 중 (PC, 30초)**
`예식 목록` → 검색으로 해당 예식 카드 → 체크리스트에서 방금 확정된 항목 체크.

**예식 당일 현장 (모바일, 수시)**
홈 화면 아이콘(PWA) → 오늘 예식 카드 → `당일` 카테고리 5항목을 진행하며 체크.
→ 모바일에서 체크박스는 44×44px 이상, 한 손 엄지 도달 범위에 배치.

## 9. 프로토타입(WeddingCheck) → 신규 전환 정리

기존 저장소는 CRM 성격의 워킹 스켈레톤입니다. 방향이 다르므로 **부분 수정이 아니라
도메인 지식만 승계하고 데이터 모델·스택을 새로 세웁니다.**

| 프로토타입 자산 | 판정 | 사유 |
| --- | --- | --- |
| 체크리스트 항목 구조 · 업무 순서 | **승계** | 현장 양식에서 나온 실물 지식 |
| D-Day 계산 · 진행률 계산 로직 | **승계** | 계산식 그대로, 기준일만 `TODAY` 고정값 → 실제 오늘로 |
| 디자인 토큰 구조 (`:root` 변수) | **승계** | 색만 rose → gold로 교체 |
| 접근성·반응형 처리 (브레이크포인트, aria) | **승계** | 검증된 값 재사용 |
| `CUSTOMERS` (이름·연락처·진행률) | **폐기** | 개인정보 |
| `MEMOS` (고객명·연락처·담당자 배정) | **재구성** | 개인정보 제거 후 자유 메모로 |
| `TASTINGS` (시식 예약 관리) | **축소** | 체크 항목 2개로 흡수 |
| 로그인 화면 · 공유 링크 · 신랑신부 화면 | **폐기** | 고객 대면 기능 |
| 사내 게시판 · 제휴업체 관리 · 실적 대시보드 | **폐기** | 회사 시스템 영역 |
| Vanilla JS + 전역 `state` + 전체 재렌더 | **교체** | Next.js + TypeScript + Zustand |
| 색 `--rose #a9455a`, Gowun Batang 세리프 | **교체** | Primary `#C8A36B`, Pretendard 단일 |

기존 저장소는 `legacy/` 로 이동해 참조용으로 보관하고, 새 앱을 루트에 세우는 것을 권장합니다.
(자세한 이관 절차는 `07-roadmap.md` §6)
